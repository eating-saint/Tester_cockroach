网站测试 —— 本机调通方案 v1
更新日期：2026-10-28
存放位置：D:\work\Bing_browse
范围：只做"本机 Windows + Chrome + 本地视觉模型"的网站测试。原生 App、多设备、企业微信都往后放。
原则：一层一层打通。每一步都有验收标准，过了再进下一步；出问题时只需要查当前这一层。


======================================================================
第 0 步：环境准备
======================================================================
需要安装：
  - Python 3.11 或更高版本
  - Chrome（日常用的那个即可；也可以另装 Chrome for Testing，专门给自动化用）
  - Ollama 0.12.7 或更高版本
  - 模型：ollama pull qwen3-vl:8b
  - Python 包：pip install websockets httpx pillow pyyaml

目录结构：
  D:\work\Bing_browse\
    profiles\      测试专用的浏览器用户目录（不碰你日常的 Chrome 配置）
    cases\         测试用例 YAML
    runs\          每次运行的截图、日志、报告
    src\           代码

验收（在命令行里逐条执行，都正常输出即通过）：
  python --version            → 3.11+
  ollama --version            → ≥ 0.12.7
  nvidia-smi                  → 能看到 5060 和 8GB 显存
  ollama run qwen3-vl:8b      → 能对话；拖一张图片进去问"图里有什么"，能答对


======================================================================
第 1 步：打通 Chrome 和 CDP
======================================================================
启动 Chrome（必须带单独的用户目录，Chrome 136 以后不带会被忽略）：
  "C:\Program Files\Google\Chrome\Application\chrome.exe" ^
     --remote-debugging-port=9222 ^
     --user-data-dir=D:\work\Bing_browse\profiles\test01

要做的：
  1. 浏览器打开 http://127.0.0.1:9222/json/version，能看到版本信息和 webSocketDebuggerUrl
  2. 用 Python 连上 websocket，发送 Page.navigate 打开朋友的点单网站
  3. 调用 Page.captureScreenshot，存成 runs\step1.png

验收：runs\step1.png 是点单网站首页的截图。


======================================================================
第 2 步：感知（结构树 + 页面状态）
======================================================================
要做的：
  1. 用 Accessibility.getFullAXTree 加 DOM 盒模型，提取可交互元素：
     按钮、输入框、链接、下拉框，每个元素带 名称 / 角色 / 位置框
  2. 订阅 Network、Log、Runtime、Page.lifecycleEvent 事件，统计：
     等待中和失败的请求数、console 报错、加载阶段
  3. 把以上内容合成 PageState，存成 runs\pagestate.json
  4. 把所有元素的位置框画到截图上，存成 runs\step2_boxes.png

验收：
  打开 step2_boxes.png，搜索框、菜品卡片、加购按钮、购物车这些关键元素都被框住，而且框的位置对得上；
  pagestate.json 里，页面加载完后等待中的请求数会降到 0。


======================================================================
第 3 步：坐标校准（最容易出问题的一步，单独做）
======================================================================
背景：笔记本 Windows 显示缩放常常是 125% 或 150%，所以截图像素、CSS 像素、模型坐标是三套不同的数值。

要做的：
  1. 读取 window.devicePixelRatio（通过 Runtime.evaluate 读一个值，不改页面）
  2. 写一个换算函数：截图像素 ↔ CSS 像素
  3. 用 Overlay.highlightRect 把 5 个已知元素的位置框高亮出来，肉眼核对
  4. 往 5 个已知元素的中心点发 CDP 点击，看点中的是不是目标元素

验收：Windows 缩放分别设成 100%、125%、150% 时，5 个元素的高亮都对得上、都能点中。


======================================================================
第 4 步：接入视觉模型
======================================================================
要做的：
  1. 截图缩放到固定宽度（例如 1280px），记录缩放比例
  2. 通过 Ollama 的 OpenAI 兼容接口（http://127.0.0.1:11434/v1）发送 base64 截图和一个问题，
     例如"搜索框在哪里，返回 JSON"
  3. 模型返回 0–1000 坐标 → 换算成截图像素 → 换算成 CSS 像素
  4. 吸附：找出包含这个点或离它最近的结构树元素，用元素的位置框
  5. 用 Overlay 高亮结果；记录耗时和显存占用

验收：
  准备 10 个目标（搜索框、某道菜、加购按钮……），统计"吸附后命中正确元素"的比例；
  记录单次调用的平均耗时和显存峰值（nvidia-smi）。
  如果 8b 显存不够，改用 4b，或者把截图再缩小一些。


======================================================================
第 5 步：执行动作
======================================================================
要做的：
  click(x,y) / type(text) / scroll() / wait() / back()
  这一步先用最简单的直线移动加点击，把整个闭环跑通；轨迹模块等第 7 步以后再换上去（接口不变）。
  每次动作前用 Overlay 高亮目标框，动作后截图。

验收：手写一串动作"点搜索框 → 输入菜名 → 回车 → 点第一个结果"，能完整跑完。


======================================================================
第 6 步：状态机 + 单条用例
======================================================================
用例格式（YAML）示例：
  - name: 搜索菜品并加购
    start_url: <点单网站地址>
    steps_goal: 搜索"宫保鸡丁"，如果结果里有这道菜就加入购物车
    expect: 购物车数量 +1，并且购物车里出现"宫保鸡丁"
    timeout: 600

状态机流程：START → CHECK → ANALYZE（问模型）→ EXECUTE → VERIFY → NEXT / FINISH
异常处理：页面没加载完就等待；动作没生效就重试（最多 N 次）；遇到验证码或人机验证就暂停，
          在命令行提示人工处理，回车后继续（企业微信以后再接）。
模型每一步只返回一个 JSON 决策；格式不合法就重新问，最多 3 次。

验收：这一条用例从头跑到尾，输出 通过或失败，以及每一步的截图和决策 JSON。


======================================================================
第 7 步：批量用例 + 报告
======================================================================
要做的：
  1. 读取 cases\ 下的所有用例，按顺序执行（母事件 = 整批用例，子事件 = 单条用例）
  2. 每条用例跑完，删掉它的上下文，只保留结果
  3. 汇总成 runs\<时间>\report.html：通过率、每条用例的耗时、失败截图、决策记录
  4. 把直线移动换成正式的轨迹模块，并在报告里加上轨迹回放

验收：一次跑 10 条以上用例，报告完整，中途失败的用例不会影响后面的用例。


======================================================================
第 8 步：Bing 条件识别测试（验证模型能力，可与第 6、7 步并行）
======================================================================
用例示例：
  - name: reddit 条件
    query: <某个词>
    condition: 结果里出现 reddit 链接
    action: 点进去，汇总评论预览文本的主要内容
    expect: 输出非空摘要，并且最终 URL 包含 reddit.com
说明：搜索间隔留长一些，免得被限流；遇到验证码就交给人工。


======================================================================
以后：Samsung 平板（安卓 App + WebView）接到这台电脑
======================================================================
关键前提（已核实，来源：developer.chrome.com/docs/devtools/remote-debugging/webviews）：
  App 里的 WebView 要能被 CDP 连上，App 必须在代码里调用
  WebView.setWebContentsDebuggingEnabled(true)。
  这个开关跟 android:debuggable 无关，正式版 App 通常没开。
  → 请朋友的开发给一个打开了这个开关的测试版 APK。这是最关键的一步。

方案 A（有测试版 APK，推荐）：
  1. 平板打开"开发者选项 → USB 调试"，USB 连到电脑，执行 adb devices 能看到设备
  2. 打开 App 进入点单页面，在电脑 Chrome 打开 chrome://inspect，能看到这个 WebView
  3. 把 WebView 的调试端口通过 adb forward 转发到本机端口，
     现有的 CDP 驱动大部分可以直接复用（感知、截图、坐标都一样）
  4. 输入改用触控事件（Input.dispatchTouchEvent），点击改成点按
  5. WebView 以外的原生部分（启动页、系统弹窗、原生按钮）用 adb 截图加 adb 点按处理

方案 B（拿不到测试版 APK）：
  1. 截图：adb exec-out screencap -p（视觉层照常工作）
  2. 结构树：uiautomator dump（WebView 里的内容只能拿到一部分，主要靠视觉模型给坐标）
  3. 输入：adb shell input tap / swipe / text
  4. 或者用 Appium UiAutomator2 统一管理（它切换到 WEBVIEW 上下文同样需要上面那个开关）
  这个方案定位精度低一些，更依赖视觉模型。

现在要做的准备：
  - 第 5 步的动作接口预留 tap / swipe，不写死成鼠标
  - 坐标换算预留"平板屏幕像素"这一套
  - 跟朋友确认能不能拿到开了 WebView 调试的测试版 APK


======================================================================
补充：任务树交给大模型管理 + 测试方法
======================================================================
[已定] 任务树（母事件 / 子事件）的内容由大模型管理，模型根据视觉做判断。
[已定] 模型能用的工具只有两类：
  任务树：create_child(目标, 完成条件) / complete(结果摘要) / fail(原因)
  动作：  click / read_text / read_image
[已定] 搜索词等需要输入的内容写在用例 YAML 里，由脚本直接填入；模型不负责输入，只判断和点击。

程序负责的硬约束（不交给模型）：
  - 同一时间只有一个节点在执行；子节点没结束，父节点不能继续
  - 树的深度有上限，每个节点的步数有上限，用完强制 fail
  - 子节点结束后，程序删掉它的上下文，只把结果摘要交回父节点
  - 模型返回的 JSON 不合法就重新问，最多 3 次

测试方法：
第一阶段：本地假网页（答案事先已知）
  - 假搜索结果页：有 reddit 链接 / 没有 reddit 链接两个版本 → 测条件判断
  - 假评论页：评论预览文字自己写好 → 测 read_text 读得准不准
  - 图片题：例如菜单是一张图片 → 测 read_image
  - 故障页：404 或一直加载不完 → 测模型能不能 fail 退回上一层
  每次运行都把任务树的变化存成 JSON，按下面四项打分：
    树结构：拆出的子任务和预期大致一致，该结束的都结束了
    点击：  点中的位置落在目标元素框里
    读取：  摘要里能找到原文的关键词（按召回率算分）
    收尾：  没有超出步数上限，出故障时能正确退回
第二阶段：少量 Bing 搜索（搜索词由脚本输入，搜索间隔留长一些）
第三阶段：朋友的点单网站
